Before any theory, test your eye. These three questions are a diagnostic, not a grade. If you get them all right, you already notice type; this guide will give you the vocabulary and the numbers behind that instinct. If you miss them, good: you now know exactly what to watch for as you read.

Diagnostic 1

Version B above feels easier to read. Which change contributes the most?

Size and leading do most of the work. At 12px with 1.2 line height, lines crowd each other and the eye slips when it returns to the left edge. The serif/sans switch matters far less than people think (Chapter 4), justification at that width causes uneven gaps but is secondary, and shorter copy helps but is a writing fix, not a typographic one.
Diagnostic 2

A dashboard shows a column of prices: ₹1,111.00 above ₹9,990.00. The digits don’t line up vertically even though the column is right-aligned. What is wrong?

In many fonts a “1” is narrower than a “9”. Proportional figures look nice in a sentence but make columns wobble. Tabular figures give every digit the same width, so places align. You will build this in Chapter 13.
Diagnostic 3

Only D uses curly quotes and apostrophes throughout, an en dash for the range, and a real ellipsis character, and it avoids mixing straight and curly marks. C mixes straight and curly quotes (and uses a spaced en dash where a colon reads better), which is the most common tell of copy pasted from a code editor. Part one

Seeing type

Before you can choose or set type well, you need to see it: the parts of a letter, the families typefaces belong to, and what actually happens in a reader’s eyes. These four chapters build the vocabulary every later decision uses.

1

Why type is most of the interface

Taught by Oliver Reichenstein, with Beatrice Warde and Robert Bringhurst

In software, typography is not decoration on top of the design; for most screens it is the design, so getting type right improves every screen at once.

In 2006 Oliver Reichenstein of Information Architects published an essay called “Web Design is 95% Typography”. His argument was simple: the overwhelming majority of what people consume on the web is written language, so the core skill of a web designer should be shaping written information. Twenty years on, the claim holds for products too. Look at a to-do app, a banking app, a settings screen or a code editor and count the pixels that are text versus everything else. Text is the interface.

This has a practical consequence for you as a solo creator. Type decisions are the highest-leverage design decisions you can make, because they are global. Change the body size, leading and colour once in your CSS or your SwiftUI text styles, and every screen improves. Polish one illustration and one screen improves. If you have limited time (you do), type is where to spend it first.

The crystal goblet

In a 1930 lecture later published as “The Crystal Goblet”, the typographer Beatrice Warde compared good typography to a clear glass: a wine lover wants a goblet that reveals the wine, not an ornate gold cup that hides it. Her point was that type in the service of reading should be invisible. The reader should notice the meaning, not the letters.

That idea is the north star for product typography, with one adjustment. In a product, type has two jobs. In reading mode (an article, a note, a long description) it should disappear. In interface mode (labels, buttons, numbers, headings) it should be instantly scannable, which means it must create clear differences: this is a heading, that is a label, this number matters more than that one. Good product typography is invisible in the first job and quietly structured in the second.

Typography exists to honor content.Robert Bringhurst, The Elements of Typographic Style

What “good” looks like on a screen

Bringhurst wrote for books, Matthew Butterick (Practical Typography) translated much of it for the web, and both agree on the goal: text that respects the reader’s time and attention. On a screen that comes down to five testable qualities, which the rest of this guide unpacks one by one:

  1. Comfortable body text. Big enough, with enough line spacing, at a line length the eye can track (Chapter 7).
  2. Clear hierarchy with few means. A small set of sizes and weights, each with a job (Chapters 8 and 9).
  3. Consistent rhythm. Spacing that follows a system, so related things sit together (Chapter 10).
  4. Correct details. Real quotes, proper dashes, aligned figures (Chapters 12 to 14).
  5. Robustness. Text that survives long names, large user font sizes, slow networks, Windows rendering and other scripts (Part five).
Key idea

Type is the one design decision that touches every screen. Fix it globally first, and decorate later, if ever.

For the solo creator

You likely design in code. That is an advantage: your type system can live in a dozen lines of CSS custom properties or a single Swift file of text styles, and every component inherits it. Spend your first design hour of any project on those dozen lines. They will outlive most of your other decisions.

Do

  • Treat type settings as global tokens you set once and reuse.
  • Judge a screen by squinting: can you still see the order?
  • Let content decide: read the real text before styling it.

Don't

  • Use type to decorate when it should inform.
  • Set sizes ad hoc per component (“this one looks better at 15px”).
  • Design with lorem ipsum; real words have real lengths and rhythms.

Audit body text first: size, contrast, leading, measure. It is the bulk of what users look at.

The anatomy of type

Taught by Erik Spiekermann, with Matthew Carter and Tobias Frere-Jones

A few measurable parts of a letter (x-height, aperture, contrast, spacing) predict almost everything about how a typeface will behave at screen sizes.

You don’t need to draw type to design with it, but you do need to see it. Spiekermann’s Stop Stealing Sheep & Find Out How Type Works exists because most people look at letters and see only “nice” or “not nice”. Designers see parts. Once you can name the parts, you can predict behaviour: this face will blur at 12px, that one will look huge at 16px, this one will turn grey and weak in dark mode.

Baseline
The invisible line letters sit on. Round letters (o, e) dip slightly below it (overshoot) so they look aligned with flat ones.
x-height
The height of lowercase letters without ascenders, like x, a, e. Because most reading happens in lowercase, x-height determines how big a face looks. Two faces at 16px can differ by 15% or more in apparent size.
Cap height
The height of flat capitals like H. Cap height matters for aligning text to icons and for all-caps labels.
Ascender and descender
The parts of b, d, h, k, l that rise above the x-height, and of g, j, p, q, y that drop below the baseline. Long extenders help word recognition but need more line spacing.
Stem
The main vertical stroke, like the uprights of H or the spine of l. Stem thickness defines weight.
Bowl and counter
The bowl is the curved stroke enclosing a space (in b, d, o, p). The counter is the enclosed or partly enclosed space itself. Small counters fill in with ink, or with blur on low-resolution screens.
Aperture
How open a partly enclosed counter is, in c, e, a, s. Open apertures keep letters distinct at small sizes.
Terminal
The end of a stroke that has no serif, like the top of a or the end of c. It can be ball-shaped, sheared, flat or tapered.
Serif
The small foot or cap at the end of a stroke. Sans serif means without.
Contrast
The difference between thick and thin strokes. High contrast looks elegant in print and large sizes; at small screen sizes the thin strokes can vanish.
Sidebearings and spacing
The built-in space on each side of a glyph. Spacing is as much part of the design as the shapes; loose spacing reads better small, tight spacing looks better large.

Why x-height matters on screens

Screens are lower resolution than print. A 16px letter on a typical display has its x-height drawn with roughly 7 to 9 pixels. Every pixel of x-height you gain makes counters bigger and shapes more distinct. That is why faces designed for screens, such as Verdana and Georgia (Matthew Carter, 1996, made for Microsoft when screens were coarse), have large x-heights and generous spacing. It is also why a classical book face like Garamond looks small and spindly at the same nominal size: its x-height is modest and its strokes are thin.

Why aperture matters

Aperture is the most underrated screen-legibility feature. In a closed-aperture face (Helvetica is the classic example), the ends of c, e, a and s curl back towards each other. That looks tidy and uniform at large sizes. At small sizes, or with blur, motion or low vision, those letters start to look like o. Humanist sans serifs (Frutiger, Source Sans, Fira) keep the apertures open, so each letter stays itself.

Contrast, terminals and other screen risks

High-contrast faces (Didot, Bodoni, Playfair Display) have hairline thin strokes. At 48px on a headline, gorgeous. At 14px on a Windows laptop, the hairlines fall below one pixel and break up. Low-contrast faces with sturdy strokes survive. Similarly, tiny distinctions like the difference between l (lowercase L), I (capital i) and 1 (one) are fine in a novel, where context resolves them, and dangerous in a password, a promo code or a file name. Atkinson Hyperlegible (Braille Institute, 2019) was designed specifically to exaggerate such distinctions for low-vision readers.

For the solo creator

Keep a one-line test string in your notes: Il1 O0 rn m a c e s 3 8 B. Paste it into any font you consider, at your smallest UI size, on the worst screen you own. Thirty seconds, and it catches most screen-legibility problems before you commit.

Do

  • Compare faces by x-height, not by nominal px.
  • Prefer open apertures and moderate contrast for UI and small text.
  • Check ambiguous glyphs wherever users copy characters.

Don't

  • Use hairline, high-contrast display faces below about 24px.
  • Assume 16px means the same size across fonts.
  • Judge a face from its marketing specimen at 72px.

    Designed for the coarse CRT screens of the 1990s, with large x-heights, wide spacing and shapes that hold up when drawn in few pixels. Screen faces are built around the pixel, not adapted to it.
  • RetinaFrere-Jones Type, for The Wall Street Journal

Common mistakes

Using a print book face for UI

It looked beautiful in a specimen at 60px.

Test at 12–16px on a non-Retina screen. Prefer faces with a screen heritage or explicit optical sizes for small text.

Swapping fonts without re-tuning size

The design tokens stay at 16px, but the new font has a 10% smaller x-height.

After any font swap, re-tune body size and line height by eye against the old version.

Ambiguous characters in codes

Recovery codes and licence keys are set in the UI font.

Use a monospace with distinct glyphs, or remove ambiguous characters from the alphabet you generate codes from.

Check yourself

Your app shows 2FA backup codes like “lO8Il1” to users who must type them on another device. People report codes “not working”. Best fix?

The failure is glyph ambiguity between l, I, 1, O and 0. A face that distinguishes them helps, and removing them from the alphabet fixes it at the source. Bold and spacing don’t change the shapes; a high-contrast serif makes it worse.

Classification: families of form

Taught by Robert Bringhurst, with Erik Spiekermann

Typefaces fall into families defined by how their strokes were made; knowing a face’s family tells you its voice, its era and how it behaves on screen before you test it.

Classification is not trivia. Each category comes from a tool and a period: the broad-nib pen of Renaissance scribes, the engraver’s steel, the industrial sign painter, the geometric ideals of the Bauhaus. Those origins left fingerprints in the shapes (where the stress falls, how much contrast there is, how open the letters are), and those fingerprints are exactly what determine screen behaviour. Learn ten categories and you can read a new typeface the way a sommelier reads a label.

The serif families

Old style faces come from the broad-nib pen, which makes thick and thin strokes depending on angle. The thinnest parts of an o sit on a diagonal (the “stress”). Contrast is modest, serifs are bracketed (they curve into the stem), and the whole thing feels warm and literary. They read well in long text, but classic old-style revivals often have small x-heights, so give them more size on screen.

Transitional faces (eighteenth century) straightened the stress towards vertical and sharpened the details. Times New Roman belongs here, and it was drawn for narrow newspaper columns, which is why it is compact.

Didones pushed contrast to the extreme: hairline serifs, vertical stress, ball terminals. Luxurious at magazine-cover sizes; fragile at text sizes on screens.

Slab serifs have thick, rectangular serifs and low contrast. Born for posters, they now include sturdy text faces (Roboto Slab, Zilla Slab) that hold up well on low-quality screens because nothing in them is thin.

The sans serif families

Grotesques were the first commercial sans serifs: slightly irregular, with some stroke contrast. Neo-grotesques (Helvetica, Univers) smoothed them into neutral, uniform shapes with horizontal terminals that curl in, which closes apertures. Humanist sans serifs bring back pen proportions and open apertures (Gill Sans, Frutiger, Myriad, Source Sans), and tend to be the most legible at small sizes. Geometric sans serifs build letters from circles and straight lines (Futura, Avenir, Jost); they are clean and stylish, but their perfectly round o, c, e and single-storey a can blur together in body text.

Most modern UI faces are hybrids. Inter is broadly neo-grotesque but with taller x-height and slightly more open forms tuned for screens. SF Pro sits between neo-grotesque and humanist. Don’t worry about precise labels; use the categories to predict behaviour.

For the solo creator

You don’t need a library of fonts. Pick one sans that is good at small sizes (humanist or a screen-tuned neo-grotesque) and, only if your product involves long reading, one serif designed for screens. That covers 95% of products. Spend the saved hours on spacing.

Do

  • Choose by behaviour (size, aperture, contrast) first and voice second.
  • Use high-contrast and display faces only at large sizes.
  • Expect modern UI faces to be hybrids; test rather than label.

Don't

  • Pick a geometric sans for long body text because it looks modern.
  • Pair two faces from the same category (two neo-grotesques fight).
  • Use a display face for anything longer than a few words.

Choosing by mood board

Long reading wants sturdy, moderate-contrast text forms designed for screens; the UI wants a clear sans with open shapes. A Didone breaks at body sizes, two neo-grotesques look like a mistake, and monospace body text is a deliberate niche choice, not a default.

Legibility, readability and how eyes read

Taught by Kevin Larson (reading research), with Walter Tracy and Keith Rayner

Reading is a series of quick jumps and short stops; typography helps when it makes each stop easy (legibility) and each jump predictable (readability).

Two words that people use interchangeably mean different things. In Walter Tracy’s classic distinction, legibility is about the typeface: how easily individual characters can be told apart. Readability is about the setting: how comfortably a block of text can be read for a long time, which depends on size, spacing, line length, contrast and layout. A highly legible face can be set unreadably (8px, justified, 140 characters wide), and a modest face set with care can read beautifully.

What the eyes actually do

Your eyes do not glide along a line. They make rapid jumps called saccades and brief stops called fixations. Eye-movement research summarized by Keith Rayner gives typical figures for skilled readers of English: fixations last around a quarter of a second, saccades jump around seven to nine characters, and somewhere around 10–15% of saccades go backwards (regressions) to re-check something. During a fixation you only see detail in a small window, a few letters to the left and more (roughly 14–15 characters) to the right. At the end of each line comes the return sweep, a long jump back to the start of the next line, which is where readers most often lose their place.

The word-shape myth

For decades designers repeated that we read by recognizing the outline of whole words (the “bouma”), and that this is why lowercase reads faster than all caps. In 2004 Kevin Larson of Microsoft’s advanced reading team published a review, The Science of Word Recognition, arguing that the evidence points elsewhere: readers recognize the letters within a word in parallel and use that information to identify the word. All-caps text is slower mostly because we have far less practice reading it, and alternating-case text slows people down because it disrupts letter recognition, not just outline.

Why this matters for you: it means letter distinctness (Chapter 2) is what you are designing for. Don’t justify all-caps paragraphs by saying “outline doesn’t matter”, and don’t justify tiny lowercase by saying “people read shapes anyway”. Make letters clear, words well spaced, and lines easy to track.

Myth

“Serif is more readable in print, sans serif on screens.” Studies comparing serif and sans for reading speed and comprehension have mostly found small or no reliable differences once size and spacing are matched. On today’s high-density screens the old pixel argument against serifs has largely gone. Choose by voice, x-height, contrast and setting, not by the serif/sans rule.

Familiarity is a feature

Readers read fastest what they read most. That is a quiet argument for conventional choices: sentence case over all caps, mixed case over small caps for long text, familiar letterforms over quirky ones (a single-storey a or a playful g may charm in a logo and slow down a paragraph). Novelty costs attention. Spend it where you want attention, never in body text.

For the solo creator

You can’t run eye-tracking studies, and you don’t need to. Read your own long screens aloud at normal speed. Wherever you stumble, lose your place or re-read, mark it. Those are your regressions and failed return sweeps, and the fix is almost always size, leading or line length.

Do

  • Separate “is the face legible?” from “is the setting readable?”
  • Design for return sweeps: moderate line length, enough leading.
  • Prefer familiar letterforms and sentence case for anything longer than a label.

Don't

  • Repeat the word-shape theory as a design rule.
  • Argue serif versus sans while body text is 13px.
  • Set paragraphs in all caps or small caps.

Common mistakes

Blaming the font

Text feels hard to read, so the font must be wrong.

Before swapping fonts, try +2px size, line-height 1.5 and a 65-character measure. Most “bad fonts” are bad settings.

Caps for emphasis in sentences

It feels like the strongest way to make something stand out.

Use weight (semibold) for emphasis in UI, italics in prose. Keep caps for very short labels.

Check yourself

Users of your docs site say long pages are tiring; they keep losing their place. Body is Inter 15px, line-height 1.3, column 1100px wide. What do you change first?

“Losing their place” is a return-sweep failure: lines are far too long (1100px at 15px is around 160 characters) and leading is tight. The face is fine. Fix the setting.

Part two

Choosing type

With the vocabulary in place, you can make the first real decision: which typefaces your product uses, how many, and under what licence. For most solo products the right answer is smaller and cheaper than you expect.

5

Choosing typefaces for a product

Taught by Matthew Butterick, with Rasmus Andersson and Oliver Reichenstein

Start from the system font and only leave it for a reason you can name; when you do leave it, choose a face built for screens that covers every size, weight, figure style and script you need.

Every font choice is a trade between three things: fit (does it suit your product’s job and voice), function (does it behave at your sizes, with your numbers, in your languages), and cost (licence, file size, loading time, maintenance). Designers new to type over-weight fit. Experienced ones start with function and cost, and let fit choose between the survivors.

Option one: the system font

Each platform ships a superb UI family: SF Pro on Apple platforms (since 2015), Segoe UI on Windows (Segoe UI Variable on Windows 11), Roboto on Android (since 2011, redesigned in 2014). On the web you reach all of them with one CSS stack, and you pay nothing in download size.

font-family: system-ui, -apple-system, "Segoe UI", Roboto,
             "Noto Sans", "Helvetica Neue", Arial, sans-serif;

What you get for free is easy to underestimate. Apple’s SF switches between Text and Display designs (and, in recent versions, uses a variable optical-size axis) and adjusts tracking by size automatically. System fonts support the platform’s Dynamic Type or text scaling. They cover many scripts, they are hinted for each platform’s renderer, and they make your app feel native because they are what everything else on the device uses.

What you give up: distinctiveness (you look like everyone), and cross-platform consistency (your web app will have slightly different widths on Mac, Windows and Android, so layouts must flex). A known wrinkle: on some Windows language settings, system-ui can resolve to a font you didn’t expect, which is one reason some teams list named fonts instead.

Option two: a chosen family

Choose a specific family when you have a reason: long reading where a serif voice matters, a brand that needs a distinctive voice, tabular data that needs particular figure features, or the need for identical metrics across platforms. Then hold the face to a function checklist before you fall for it.

The function checklist

Pairing, superfamilies and licences

Taught by Erik Spiekermann, with Matthew Butterick

One family is usually enough; when you pair, combine clear contrast in structure with shared proportions, and give each face a distinct job.

Pairing advice is full of folklore (“always pair a serif with a sans”). The underlying logic is simpler. Two faces on one screen should either be clearly the same (one family) or clearly different (contrasting structure). The failure zone is in between: two faces that are almost alike, so the reader senses a difference but can’t tell what it means. That reads as a mistake.

Rules that actually explain pairings

  1. Start with one family. A good family with three or four weights and italics gives you more hierarchy than most products need (Chapter 9).
  2. If you pair, contrast structure. Serif with sans, or a display face with a text face. Not two neo-grotesques.
  3. Share proportions. Faces with similar x-height ratio and width sit comfortably on the same line and in adjacent blocks. Mismatched x-heights make one look shrunken.
  4. Share an era or a construction logic when possible. A humanist sans (pen proportions) pairs naturally with an old-style or modern humanist serif. A geometric sans sits well with a didone or a geometric slab.
  5. Give each face a job. “Serif for reading, sans for interface” or “display for page titles only”. If you can’t state a face’s job, you don’t need it.
  6. Prefer superfamilies. IBM Plex, Source, Noto and Roboto (Roboto, Roboto Slab, Roboto Mono, Roboto Serif) were designed to work together, with matched metrics. The pairing work is already done.

Size, leading and measure

Taught by Robert Bringhurst, with Matthew Butterick

Body text reads best at 16–20px on screens, with line-height around 1.4–1.6, on lines of 45–75 characters; and the three numbers depend on each other.

These are the three settings that decide whether a paragraph is comfortable. They are not independent. A bigger size needs a longer line in px to keep the same characters per line. A longer line needs more leading so the return sweep (Chapter 4) can find the next line. A face with a tall x-height looks bigger and needs more leading than one with a small x-height. Tune them together.

Size: start at 16, often go higher

Browsers default to 16px, and that is a floor for body text on the web, not a target. Butterick suggests 15–25px for web body text; many reading-focused sites sit at 18–21px. On iOS the default Body text style is 17pt; Android’s Material body sizes are around 14–16sp. People hold phones closer than they sit to laptops, so similar numbers work on both. Text smaller than about 12–13px should be rare and never essential.

Leading: the space between lines

“Leading” comes from the strips of lead typesetters put between lines of metal type. In CSS it is line-height, best written unitless (1.5, not 24px) so it scales with size. For body text, 1.4–1.6 is the usual band; Butterick suggests 120–145% of the point size, and WCAG’s enhanced criterion asks for at least 1.5 within paragraphs. Use the low end for short lines and small x-heights, the high end for long lines and tall x-heights. Headings need less: 1.1–1.25, because large sizes already create space and loose headings fall apart into separate lines.

Measure: characters per line

Bringhurst gives the classic range: 45 to 75 characters per line (counting letters and spaces) for single-column text, with around 66 often cited as ideal. Shorter lines force constant return sweeps and choppy reading; longer lines make the sweep long and error-prone. In CSS set it with max-width in em or ch. Note that ch is the width of the digit zero, which is usually wider than an average letter, so 66ch typically gives somewhat more than 66 real characters. Test with real text, as the lab below does.

Lab: readability (size, leading, measure, face)

Reading is not a smooth glide. Your eyes jump a few words at a time, pause for a fraction of a second, and at the end of every line make a long sweep back to the left edge to find the next one. When lines are too long, that sweep misses; when they are packed too tightly, the target is too small to hit. Comfortable text is not about a beautiful font so much as about three numbers chosen together: how big the letters are, how much air sits between the lines, and how many characters each line carries before it turns.

Leading relative to measure

The lab’s suggestion follows a simple principle: the longer the line, the more leading it needs. A 40-character mobile column can live at 1.4; a 75-character desktop column wants 1.6 or more. Text with a tall x-height (Inter, Atkinson, Verdana) looks tighter at the same line-height, because the gap between lines (from baseline to the next line’s x-height) is smaller; give it 0.05–0.1 more.

Paragraph spacing or indent, never both

Paragraphs need a signal that a new one has begun. Either add space between them (on screens, typically 0.75–1em, smaller than a full blank line is fine), or indent the first line (1–2em) with no extra space, as books do. Using both double-signals and wastes space. On screens, and especially in UI and documentation, spacing is the norm because text is scanned as much as read. First-line indents suit continuous reading like fiction and long essays.

Key idea

Size, leading and measure are one decision with three dials. Move one, re-check the other two.

  • Tighten leading for headings (1.1–1.25).

  • Set body text below 16px on the web to “fit more”.
  • Inherit body line-height (1.5) into 40px headings.

Type scales: a few sizes, related

Taught by Tim Brown (modular scales), with Robert Bringhurst

Pick five to seven sizes related by a consistent ratio, give each a job, and use nothing else; the relationship between sizes is what makes hierarchy feel intentional.

Look at a product built without a scale and you’ll find 11px, 12px, 13px, 14px, 15px, 16px, 17px, 18px, 20px, 22px, 24px and 28px, each chosen once for one component. The result looks slightly off everywhere, because neighbouring sizes are too close to read as different levels and too far to read as the same. A scale fixes this by making every size a deliberate step.

Modular scales

Bringhurst described the classical scale of sizes used by printers since the sixteenth century, and in 2011 Tim Brown’s article “More Meaningful Typography” (A List Apart) and his modularscale.com tool popularised the idea for the web: start with a base size and multiply by a ratio. Keep body text nearly fixed (it should not shrink on phones) and let display sizes flex.

A scale is a vocabulary. Small vocabularies are easier to speak consistently.

  • Generate sizes from a ratio, then round and hand-tune.

Hierarchy without shouting

Taught by Massimo Vignelli, with Erik Spiekermann

Size is only one of six levers for typographic hierarchy; calm interfaces use weight, colour, case, space and position for most distinctions, and change only one or two levers per level.

Vignelli was famous for working with very few typefaces and a few sizes, and still producing rich, clear hierarchy. The trick is that hierarchy is about difference, and size is the loudest, most space-hungry way to make a difference. In a dense product screen you have many small distinctions to make (title vs metadata, label vs value, active vs inactive), and if all of them use size you end up with a dozen sizes and a noisy page. See Visual Design for hierarchy in layout; this chapter covers the typographic levers.

Emphasis by subtraction

Beginners make important things bigger and bolder. Experienced designers more often make unimportant things quieter: smaller, lighter, muted grey. The effect is the same contrast, but the page gets calmer instead of louder. A list item with a 15px semibold title and a 13px muted line of metadata has clear hierarchy without any big type.

Be careful with grey. Muted text still has to meet contrast requirements (4.5:1 for normal text under WCAG AA); “subtle” #AAA on white fails. Use one or two defined text colours (primary and secondary), not a gradient of greys. See Accessible & Inclusive for the contrast details.

Vertical rhythm and spacing

Taught by Robert Bringhurst, with Josef Müller-Brockmann

Space between text elements should come from a small set of related values, and space above a heading should be larger than space below it, so headings belong to what follows.

Bringhurst compares the page to music: the rhythm of lines and spaces should be steady, and departures from it should be meaningful. In print, typographers lock every line to a baseline grid so lines on facing pages align. On screens, a strict baseline grid is harder (and less valuable), but the underlying idea is essential: spacing should be systematic, and it should express relationships.

The heading proximity rule

A heading labels the content below it, so it should sit closer to that content than to the content above. A common ratio is about 2:1 (for example 32px above, 12–16px below). When the spaces are equal, the heading floats ambiguously between two sections, and users have to read it to know where it belongs. This is the Gestalt principle of proximity (see The Human Mind) applied to type.

A spacing system from your line-height

The simplest rhythm on screens: derive spacing from a base unit (commonly 4px or 8px) and keep line-heights on that unit too. If body text is 18px with line-height 1.5, a line is 27px, which doesn’t sit on a 4px grid; 18px × 1.556 ≈ 28px does. Many teams round line-heights in px to multiples of 4 for each text style (body 28, small 20, title 32, heading 40) and use spacing tokens of 4, 8, 12, 16, 24, 32, 48, 64. Then everything snaps to one invisible rhythm and nothing looks “a bit off”.

Why exact baseline grids are hard on the web

CSS centres text inside its line box: half the extra leading goes above, half below (“half-leading”), and the font’s own ascent and descent metrics add more invisible space. So the visible top of a capital letter is not at the top of the box. That is why a button label can look slightly low even when padding is “equal”, and why aligning text to an icon needs care. Tools such as Capsize compute trims from font metrics, and newer browsers support the text-box properties (text-box-trim and text-box-edge) that cut the box down to cap height and baseline. Use them for precise component alignment; don’t chase a perfect page-wide baseline grid in a complex app.

For the solo creator

Don’t build a baseline-grid framework. Do this instead: spacing tokens on a 4px base, line-heights per text style rounded to 4px, and the 2:1 heading rule. Turn on a 4px grid overlay in your browser dev tools once a month and look for strays.

Do

  • Put more space above headings than below.
  • Use a small set of spacing tokens tied to a base unit.
  • Trim text boxes (or nudge) when aligning text with icons.

Don't

  • Use arbitrary margins like 13px or 22px.
  • Let heading margins equal paragraph margins.
  • Force a rigid baseline grid onto dense, mixed-size UI.

Alignment, rag and wrapping

Taught by Matthew Butterick, with Robert Bringhurst

On screens, set text flush left and ragged right by default; justify only with good hyphenation and a generous measure, and let the browser balance headings and avoid stranded last words.

Justified text, with both edges straight, looks orderly in books because book typesetting engines adjust spacing across a whole paragraph, hyphenate carefully, and may even subtly adjust letter spacing. Browsers mostly do something simpler: they break lines one at a time and stretch the word spaces on each line to fill it. On narrow columns, that produces irregular gaps and sometimes “rivers”, channels of white that run down through the paragraph and pull the eye vertically.

When justification is fine

Justified text can work on screens when three conditions hold: the measure is generous (60+ characters), hyphenation is on (hyphens: auto with a correct lang attribute on the page or element), and the content is continuous reading (an e-book, a long essay) where a book-like texture is part of the experience. E-readers such as Kindle justify by default with hyphenation. For UI, docs and anything narrow or mixed with code and links, ragged right is better. WCAG’s enhanced criterion (1.4.8) lists “not justified” among its visual presentation requirements, because uneven spacing makes reading harder for some people, including many dyslexic readers.

Lab: justified vs ragged, with hyphenation

Typographers have argued about justification for centuries. In a well-made book, the compositor balances spacing across the whole paragraph and hyphenates carefully, so the texture stays even. Browsers typically break lines one at a time and stretch the spaces, which in narrow columns opens irregular gaps and occasionally a river of white running down the page. Hyphenation helps, because breaking long words gives the line breaker more choices. Characteristically, administrative, internationalization and responsibility are the kind of words that cause trouble.

Start at 300px, justified, hyphenation off: look for big gaps. Turn hyphenation on and watch them shrink. Then widen to 600px and notice justification becomes acceptable. “Pretty” wrapping (where supported) avoids a single stranded word on the last line.

Shaping the rag

Ragged right isn’t carefree. A good rag ripples gently; a bad one has deep notches or a staircase shape. On the web you can’t hand-tune each paragraph, but you can help: keep the measure in range, enable hyphenation for long-word languages (German, Dutch) and narrow mobile columns, and use non-breaking spaces to keep small units together (“10 MB”, “Mr. Sharma”, “Chapter 7”).

Widows, orphans and stranded words

In print, an orphan is a paragraph’s first line left alone at the bottom of a page and a widow is its last line alone at the top of the next (definitions vary between sources, which is why many people just say “stranded lines”). On the web, the everyday problem is a single short word alone on the last line of a paragraph or heading (sometimes called a “runt”). CSS now helps: text-wrap: balance evens out line lengths in short blocks like headings and captions, and text-wrap: pretty asks the browser to avoid very short last lines in paragraphs. Balance is widely supported; pretty is newer, so treat both as progressive enhancement.

Centred and right-aligned text

Centred text has two ragged edges, so every return sweep must find a new starting point. It works for short, symmetrical things (a dialog title, a two-line empty state, a poster headline) and fails for anything over about three lines. Right alignment is for numbers in tables (Chapter 13) and for labels hugging a value, not for paragraphs (in left-to-right languages).

Key idea

The eye trusts even word spacing more than straight edges. Keep the spaces even; let the edge breathe.

For the solo creator

Three lines of CSS cover most of this chapter: h1,h2,h3{text-wrap:balance}, p{text-wrap:pretty}, and html{lang} set correctly so hyphenation and quotes work when you need them. Add hyphens:auto only on narrow mobile columns or long-word languages.

  • Balance headings and avoid stranded last words.
  • Use non-breaking spaces between numbers and units.

Don't

  • Justify narrow columns without hyphenation.
  • Centre paragraphs longer than three lines.
  • Fix rag by inserting manual line breaks that break on other screens.

Quotes, dashes and the small marks

Taught by Matthew Butterick, with Robert Bringhurst

Straight quotes, double hyphens and three dots are typewriter substitutes; real typography uses curly quotes, true apostrophes, the right dash for each job and a real ellipsis, except in code, where straight characters are correct.

Typewriters had a limited keyboard, so one key served for opening quotes, closing quotes, apostrophes, feet and inches. Computers inherited that keyboard. Butterick calls straight quotes and apostrophes the most visible sign of careless typography, because they look like what they are: a mechanical compromise. Your product’s microcopy is read millions of times. Getting these marks right costs almost nothing once you know them.

The dashes

There are three common horizontal marks and they are not interchangeable. The hyphen (-) joins words (“well-known”, “sign-in page”) and breaks words at line ends. The en dash (–), about the width of an n, marks ranges and connections: “9–5”, “Mumbai–Pune”, “pages 12–18”. The em dash, about the width of an M, marks a strong break in a sentence (shown in the figure above). Many writers overuse the em dash; in UI copy, a colon, comma or full stop is often clearer. The minus sign (−) is a fourth mark, as wide as a plus sign, for negative numbers in data: −₹1,200 lines up with +₹1,200, while a hyphen looks short and weak.

Spaces you didn’t know existed

A non-breaking space (&nbsp;, U+00A0) looks like a normal space but forbids a line break, so “10 MB”, “₹ 500” (if you space it), “Fig. 3” and “iOS 18” never split across lines. A thin space (U+2009) is useful around some marks and between number groups in some locales. One space after a full stop, never two; the double space is another typewriter habit.

Figures, small caps and OpenType features

Taught by Tobias Frere-Jones, with Edward Tufte and Rasmus Andersson

Most good fonts hide several versions of their numerals and other alternates; choose tabular lining figures for data, proportional or old-style figures for prose, and use real small caps and fractions instead of fakes.

Numbers are everywhere in products: prices, dates, counts, durations, versions. Fonts usually include at least two sets of digits, and many include four, selected with OpenType features. Using the right set is one of those details that makes an interface feel engineered rather than assembled.

Tabular vs proportional

In CSS: font-variant-numeric: tabular-nums. Fonts differ in their defaults: Inter defaults to proportional figures (tabular are one feature away), while the Google Fonts versions of Source Serif 4 and EB Garamond default to tabular. Tracking, kerning, optical sizes and variable fonts

Taught by Matthew Carter, with Erik Spiekermann and Tobias Frere-Jones

Fonts are spaced for lowercase text at one size range; capitals, very small text and very large text all need spacing adjustments, and optical sizes and variable fonts let the font itself adapt.

A type designer spends as long on spacing as on shapes. The spacing is tuned for lowercase text around reading sizes. Move away from that sweet spot and the spacing stops fitting. Two adjustments fix it: tracking (uniform letter-spacing across a run of text, letter-spacing in CSS) and kerning (adjustments between specific pairs like “AV” or “To”, built into the font and on by default in browsers).

The three tracking rules

  1. All caps and small caps: add tracking. Capitals are designed to sit next to lowercase, so in a row of capitals they crowd. Butterick suggests 5–12% extra; in CSS, letter-spacing: 0.05em to 0.12em. The smaller the caps, the more they need.
  2. Large display text: reduce tracking slightly. At 40px and above, default spacing looks loose. Try −0.01em to −0.03em. Never so tight that letters touch.
  3. Small text: add a touch. Below about 13px, a hair of extra spacing (0.01–0.02em) helps letters stay distinct. Apple’s SF does this automatically by size.

Never track lowercase body text for “style”: it breaks up word shapes and slows reading. And note a CSS detail: when you add letter-spacing, browsers turn off optional ligatures, which is what you want for spaced caps.

Optical sizes

In metal type, each size was cut separately: small sizes had larger x-heights, sturdier hairlines, looser spacing; large sizes were finer and tighter. Digital fonts lost that when one outline was scaled to every size. Optical sizes bring it back. Some families ship separate cuts (SF Pro Text and SF Pro Display; Inter and Inter Display), and variable fonts can have an opsz axis that the browser sets automatically from the font size (font-optical-sizing: auto, the default). This page’s body text, Source Serif 4, has an opsz axis: the headings and body you are reading are slightly different designs.

Variable fonts

A variable font is one file containing a continuous design space along axes. The registered axes are weight (wght), width (wdth), optical size (opsz), italic (ital) and slant (slnt); fonts may add custom ones, such as grade (GRAD), which changes weight without changing width. For a product this means: one file instead of six, any weight you like (550 if 500 is too light and 600 too heavy), automatic optical sizing, and tricks like adjusting grade in dark mode (Chapter 18). Use font-weight, font-stretch and font-optical-sizing when possible; drop to font-variation-settings only for custom axes.

Key idea

Caps need air, big text needs less, small text a touch more. Let optical sizes do the rest.

For the solo creator

Do

  • Track all-caps labels 5–12%.
  • Tighten large display headings slightly.
  • Prefer variable fonts with an opsz axis for products with wide size ranges.

Don't

  • Track lowercase body text.
  • Turn off kerning (it’s on by default; leave it).
  • Use one weight of a display cut for small UI text.

UI typography: labels, buttons, truncation and user font sizes

Taught by Apple’s Human Interface Guidelines, with Material Design and Loren Brichter

Interface text is short, functional and unpredictable in length; design it to be scannable at small sizes, to wrap or truncate gracefully, and to grow when the user asks for bigger text.

Reading typography optimizes a paragraph you control. UI typography handles hundreds of tiny strings you don’t: a user’s name that might be “Li” or “Venkatanarasimharajuvaripeta”, a translated button label 40% longer than English, a price with seven digits, a user who has set their phone to the largest text size. The craft here is less about beauty and more about resilience.

Labels, buttons and captions

  • Labels sit close to what they label (proximity), in a quieter style than the value: smaller or muted, rarely both. Sentence case reads fastest.
  • Buttons use a verb, sentence or title case, and medium or semibold weight at body size or slightly smaller. Keep the label visually centred (mind the invisible line box from Chapter 10) and give it padding in em so it grows with text.
  • Captions and helper text are the smallest size in your scale, but not below 12px on the web (Apple’s smallest style is 11pt) and with enough contrast to read.
  • Numbers in UI are often the most important element on a screen (a balance, a count, a temperature). Let them be the largest text, in tabular figures, with units smaller and muted.

Wrapping vs truncation

When text is longer than its space, you have three options: wrap it, truncate it, or let it overflow (never). The default should be wrap: it keeps all the information and adapts to translations and large text. Truncate only where a fixed height matters for scanning (list rows, tabs, table cells), and then:

  • Truncate at the end for titles and names (“Quarterly planning for the…”), using an ellipsis, and give the full text on hover, focus, or the detail view.
  • Truncate in the middle for file names and paths, where the end carries meaning (“Invoice_2026…final_v3.pdf”), as macOS Finder does.
  • Clamp multi-line previews (-webkit-line-clamp / line-clamp) to two or three lines, not one.
  • Never truncate numbers, prices, dates or anything a user must compare or act on.

Dynamic Type and user font sizes

Many people enlarge text: on iOS through Dynamic Type (from the default “Large”, where Body is 17pt, up through accessibility sizes where Body reaches about 53pt), on Android with the font scale setting, on the web with browser zoom and default font size. WCAG requires that text can be resized to 200% without loss of content or function. Your layout must survive. That means: sizes in relative units (rem on the web, text styles on native), no fixed heights on text containers, buttons that grow, rows that wrap, and layouts that switch from horizontal to vertical when text gets big (iOS apps commonly stack label and value at accessibility sizes).

Rendering and loading

Taught by Matthew Carter (on screen fonts), with web performance practice

The same font looks different on macOS, Windows and Android, and it may arrive late or not at all; test on real platforms and load fonts so text is readable immediately and doesn’t jump when the font arrives.

Why your font looks different on Windows

Text rendering turns ideal outlines into pixels, and platforms make different trade-offs. macOS has long favoured fidelity to the outline shape, which looks smooth and slightly heavier and blurrier; since macOS Mojave (2018) it no longer uses subpixel antialiasing by default, so text on non-Retina Mac screens looks lighter than it used to. Windows, with ClearType and DirectWrite, has favoured snapping strokes to the pixel grid for sharpness, which relies more on hinting (instructions in the font that tell the rasterizer how to fit the grid). A font with poor hinting can look crisp on a Mac and ragged or thin on a Windows laptop. On high-density screens (2x and above) these differences shrink a lot; on the 1x office monitors many people still use, they matter.

A CSS note: -webkit-font-smoothing: antialiased only affects macOS browsers, making text look lighter. Many sites set it globally; it can help light text on dark backgrounds, but on a light background it often makes body text too thin. Use it deliberately, not by habit.

Font loading: FOIT, FOUT and layout shift

Web fonts download after the page starts rendering. Browsers then choose between two failure modes. FOIT (flash of invisible text): text is hidden until the font arrives, typically for up to about three seconds, and on a slow connection users stare at a blank page. FOUT (flash of unstyled text): text shows in a fallback font immediately and swaps when the web font loads, which may shift the layout. You control this with font-display in @font-face:

A loading recipe

  1. Self-host WOFF2 files from your own domain (fast, private, no third-party dependency).
  2. Subset to the characters and scripts you need (with unicode-range so other scripts load only on demand), but keep the OpenType features you use.
  3. Use one variable file instead of many static weights where you can.
  4. Preload the one or two files needed above the fold: <link rel="preload" as="font" type="font/woff2" crossorigin>.
  5. Set font-display: swap (or optional) and define a fallback @font-face that uses a local font with size-adjust, ascent-override and descent-override so its metrics match. Several frameworks (for example Next.js’s font tooling) generate these for you.
For the solo creator

The system font stack has zero loading cost, zero layout shift and zero licence risk. If you choose a web font, budget one afternoon to do the recipe properly once, put it in your project template, and never think about it again. Test with your browser’s network throttling set to “Slow 4G”.

Do

  • Test on a Windows machine and a 1x screen, not only on a Retina Mac.
  • Self-host, subset, preload and use swap or optional.
  • Match fallback metrics to avoid layout shift.

Don't

  • Hide text while fonts load.
  • Ship nine static weights “just in case”.
  • Set -webkit-font-smoothing: antialiased globally without checking light mode body text.

Many scripts: Devanagari, mixed text and localization

Taught by Indian Type Foundry and Ek Type (Indic type design), with Google’s Noto project

Other scripts have different shapes, heights and rules; give them fonts designed for them, enough line height for their marks, and sizes matched by eye to your Latin text.

If your product might be used in India, Hindi, Marathi, Bengali, Tamil, Telugu and other Indian languages are not an edge case. Even an English-first app shows Indian names, addresses and user-generated text. The Latin rules in this guide don’t transfer automatically. Devanagari, used for Hindi, Marathi, Nepali and Sanskrit, is a good example of why.

How Devanagari differs

  • The headline (shirorekha). Most letters hang from a horizontal line at the top, which joins letters into words. Visually, the “x-height” is the body between the headline and the baseline.
  • Marks above and below. Vowel signs (matras) and other marks sit above the headline and below the baseline, and conjuncts stack. That needs more vertical room than Latin: line-height around 1.6–1.8 for body text, versus 1.4–1.6 for Latin.
  • Apparent size. At the same font-size, Devanagari often looks smaller than Latin because the main body is a smaller fraction of the em. It commonly needs a slightly larger size (often 10–15% more) to feel equal.
  • Shaping. Letters change form in combination (conjuncts, reordering of vowel signs). This requires proper OpenType shaping, which modern browsers and OSes do, but which breaks if you letter-space, fake bold or cut strings in the middle of a grapheme cluster.
  • No case. There are no capitals, so all-caps styling and tracking rules don’t apply; use weight and size for hierarchy.

The Hindi sample reads: “Your order has been sent. You can see the delivery status on the order page, and contact us if there is a mistake in the address.”

Fonts for Indian scripts

Use a font designed for the script, not whatever the system falls back to. Good free options: the Noto families (Noto Sans Devanagari, Noto Serif Devanagari, and Noto for Bengali, Tamil, Telugu, Kannada, Malayalam, Gujarati, Gurmukhi and Odia), which aim at broad, consistent coverage; Hind and other families from Indian Type Foundry; Mukta from Ek Type; and IBM Plex Sans Devanagari, which matches IBM Plex Sans. Many of these were designed alongside a Latin companion, so the two scripts sit together well.

Mixed scripts on one screen

When a user’s Hindi name appears in an English UI, or an English brand name appears in Hindi text, two fonts share a line. Make it work by: listing a script-specific font in the stack (CSS picks per character, so font-family: Inter, "Noto Sans Devanagari", sans-serif uses Inter for Latin and Noto for Devanagari); setting lang attributes on content in other languages (this drives font selection, hyphenation and screen reader pronunciation); sizing so both scripts look the same size; and setting line-height for the taller script wherever it might appear.

Localization beyond Indian scripts

  • Expansion: translated strings are often 30% longer or more (German, Finnish); short English labels can double. Wrap, don’t clip (Chapter 15).
  • CJK: Chinese, Japanese and Korean text has no word spaces, wraps between most characters, needs larger fonts (fonts are big files; rely on system fonts or careful subsetting), and has its own punctuation rules. WCAG’s line-length guidance is 40 characters for CJK versus 80 for Latin.
  • Right-to-left: Arabic and Hebrew mirror layouts; use logical CSS properties (margin-inline-start, text-align: start) so your layout flips correctly.
  • Numerals and formatting: dates, numbers and currency vary by locale; always use locale-aware formatters.
For the solo creator

Even if you only ship English, add a Devanagari font to your fallback stack and set line-heights that won’t crush Indian names in user content. If you localize, start with one Indian language and test with a native reader; a single ten-minute session will teach you more than any rule.

Do

  • Use fonts designed for each script you support.
  • Give Devanagari and other Indic scripts more line height and slightly larger size.
  • Mark languages with lang and use logical CSS properties.

Don't

  • Letter-space or fake-bold complex scripts.
  • Truncate strings by character count (you may cut a cluster in half).
  • Assume Latin metrics and spacing work for every script.

Monospace, code and type in dark mode

Taught by Oliver Reichenstein, with Matthew Butterick

Code needs a monospace with unmistakable characters set slightly smaller than body text; dark mode needs slightly lighter weights and softer contrast, because light text on dark looks bolder and glows.

Choosing a code font

In code, every character carries meaning and readers scan vertically for alignment, so monospace (every glyph the same width) is the norm. What separates a good code font: distinct 0 O, 1 l I, and { } ( ) [ ]; punctuation big enough to see (a comma vs a full stop matters); a generous x-height; and enough weight to survive dark themes. Good choices include SF Mono and Menlo (Apple), Consolas and Cascadia Code (Microsoft), JetBrains Mono, IBM Plex Mono, Fira Code and Source Code Pro. For a web stack, ui-monospace, "SF Mono", Menlo, Consolas, monospace gives a good native mono on each platform, as this course uses.

Setting code

  • Size it down. Monospace looks bigger than proportional text at the same size because it is wider. Inline code usually sits at 0.85–0.9em of the surrounding text (this page uses 0.86em).
  • Leading 1.5–1.6 for code blocks; tight code is hard to scan.
  • Don’t wrap code by default in blocks; scroll horizontally, and keep lines short in examples you write.
  • Ligatures are a choice. Programming ligatures (Fira Code, JetBrains Mono, Cascadia Code) turn != or => into single symbols. Some developers love them; Butterick argued against them in an essay because they can misrepresent the actual characters. In a product that shows code to others, leave them off; in an editor, make them a setting.

Monospace for writing

iA Writer made a deliberate, debated choice: a monospace-derived face for prose writing. The argument is that monospace slows the eye slightly and makes the text feel like a draft, which encourages writing rather than admiring. iA later designed Duo (a few wide letters like m and w get extra width) and Quattro (closer to proportional) to keep that “draft” feel while reducing monospace’s gappy texture. The lesson for your product isn’t “use monospace”; it is that a font’s texture changes how people feel about the act they perform. Choose texture for the job.

Type in dark mode

Light text on a dark background looks heavier and slightly blurred than the same text dark-on-light. Part of this is perceptual (bright areas appear to spread into dark ones, an effect often called irradiation), part is rendering, and for people with astigmatism very bright text on black can appear to glow or smear (halation). Three adjustments help:

  1. Soften the extremes. Avoid pure white (#FFF) on pure black (#000). Off-white on a very dark grey keeps contrast well above 4.5:1 while reducing glare.
  2. Lighten weight slightly. If body text is 400 in light mode, it can look like 450 in dark mode. Variable fonts with a grade axis let you reduce apparent weight without changing width; otherwise consider one step lighter for large text, and check thin weights don’t disappear.
  3. Re-check muted text. Secondary greys tuned for light mode often fail or look muddy in dark mode. Define them separately (this course defines every colour token twice).

Wrap-up

Ten things to remember

  1. Type is most of your interface; type settings are the highest-leverage, most global design decisions you make.
  2. X-height, aperture, contrast and spacing predict how a face behaves on screens. Judge faces by these, not by their specimen.
  3. Legibility is the face; readability is the setting. Most problems are settings, and settings are free to fix.
  4. Start with the system font; leave it only for a reason you can name. One family is usually enough.
  5. Body 16–20px, line-height 1.4–1.6, 45–75 characters per line, tuned together.
  6. Five to seven named sizes from a gentle scale; weight, colour and space for the minor levels.
  7. More space above headings than below; spacing from tokens on one base unit.
  8. Ragged right by default; balance headings; justify only with hyphenation and width.
  9. Curly quotes, real dashes and ellipses in prose; tabular figures for data; tracked caps; straight characters in code.
  10. Make type robust: user text sizes, long strings, Windows rendering, slow fonts, Indian scripts and dark mode.

Practice assignment for the next two weeks

Typography improves with daily looking and weekly doing. Spend about 20 minutes a day.

  1. Days 1–3: See. Each day, screenshot one screen from an app you admire and one you don’t. Annotate size, leading, measure, scale steps, weights and one detail (quotes, figures, tracking). Use this guide’s vocabulary.
  2. Days 4–5: Decide. Write your type decision record (Exercise 5.1) and set body tokens (Exercise 7.1).
  3. Days 6–8: Systematize. Collapse your sizes into a named scale (8.1), fix spacing (10.1) and hierarchy (9.1).
  4. Days 9–10: Detail. Punctuation sweep (12.1), number audit (13.1), tracking tokens (14.1).
  5. Days 11–13: Harden. Stress fixtures at 200% (15.1), loading and Windows check (16.1), script test (17.1), dark mode pass (18.1).
  6. Day 14: Show. Run the six-step worked example on your longest screen (19.1), complete the type audit checklist, and put a before/after strip somewhere you’ll see it.

Reading list

  • The Elements of Typographic Style
    Robert Bringhurst (1992, later editions) · The classic on text typography: measure, rhythm, scale, details. Print-oriented but the principles transfer.
  • Butterick’s Practical Typography
    Matthew Butterick (free online) · Blunt, practical rules with numbers; the fastest way to fix everyday text. Read the summary page first.
  • Stop Stealing Sheep & Find Out How Type Works
    Erik Spiekermann and E. M. Ginger · A friendly, visual introduction to seeing and choosing type.
  • Thinking with Type
    Ellen Lupton · Letter, text, grid, with many visual examples; good for building vocabulary.
  • On Web Typography
    Jason Santa Maria (A Book Apart, 2014) · Choosing and pairing type for screens, with a designer’s eye.
  • Web Typography
    Richard Rutter (2017) · Detailed, technical guide to setting type with CSS, from measure to OpenType features.
  • “Web Design is 95% Typography”
    Oliver Reichenstein, Information Architects (2006) · The short essay that frames this whole guide.
  • “The Crystal Goblet”
    Beatrice Warde (1930 lecture) · Why type in the service of reading should be invisible.
  • “The Science of Word Recognition”
    Kevin Larson, Microsoft (2004) · The readable research review behind Chapter 4’s word-shape discussion.
  • “More Meaningful Typography”
    Tim Brown, A List Apart (2011) · The article that brought modular scales to web design.
  • Typeface Mechanics series
    Tobias Frere-Jones (essays on his studio’s site) · How type designers solve overshoot, spacing and other optical problems.
  • Apple Human Interface Guidelines: Typography, and Material Design 3: Typography
    Apple; Google · The platform rules for text styles, sizes and dynamic type you’ll build against.
